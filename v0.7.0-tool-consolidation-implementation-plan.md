# v0.7.0 Tool Consolidation And Collaborative Editing Plan

## Goal

Ship the inline collaborative editing workflow as a real AssistantMD file
operation capability, not as a parallel proposal tool or spike tool.

Version `0.7.0` is a breaking-change release because it changes the model-facing
tool contract and the script/direct-tool surface:

- replace `file_ops_safe` and `file_ops_unsafe` with structured `file_read`
  and `file_write` tools;
- remove `propose_file_edits`;
- remove the temporary `review_create_file` spike tool;
- remove per-chat tool selection from the UI;
- replace `default_chat_tools` with app-wide `enabled_tools`;
- add a chat-level mode toggle for normal versus collaborative editing.

The desired user-visible outcome is simple:

1. Normal chats behave like today: the agent can write through enabled tools.
2. Collaborative chats route `file_write` operations through inline review
   cards.
3. Batch file edits use the real write operation tool and render as one
   multi-row review card.
4. Approved review cards resume the same agentic turn so multi-step work
   continues naturally.

## Product Decisions

### Chat Modes

Use two chat modes:

- `normal`: default behavior. Enabled tools are available and mutating file
  operations execute directly.
- `collaborative`: `file_write` operations defer into inline review cards
  for user inspection, editing, approval, or denial.

This is a chat workflow preference, not a system-level permission model. The UI
should expose it near the chat composer or chat controls, not buried in the
System tab.

The agent may receive a concise mode instruction when collaborative mode is
active, for example:

> Collaborative edit mode is active. Use reviewed file operations for vault
> changes so the user can inspect and adjust edits inline.

This is product guidance, not a security boundary. `code_execution` does not need
to be disabled for the initial implementation unless live testing shows it
regularly undermines the intended workflow.

### Tool Availability

Replace `default_chat_tools` with `enabled_tools`.

`enabled_tools` is a list setting. It is app-wide, not chat-specific:

- chat agents receive enabled chat-visible tools automatically;
- delegate and other model tool-binding surfaces must honor it;
- Monty scripts and context scripts can only call direct tool functions for
  enabled tools;
- disabled means disabled across the application.

Scripts do not declare tools. They call available direct tool functions
explicitly. The enabled-tool registry controls which direct functions exist.

### File Tool Boundary

Introduce two model-facing file tools:

- `file_read`: read-only inspection operations.
- `file_write`: mutating operations, including batch.

This split matches Pydantic AI's tool-level deferred approval model. In
collaborative mode, `file_write` can be deferred while `file_read` remains
immediate.

`file_read` operation set:

- `read`
- `list`
- `search`
- `frontmatter`

`file_write` operation set:

- `write`
- `append`
- `edit_line`
- `replace_text`
- `move`
- `delete`
- `mkdir`
- `batch`

Use concrete command-style operation names that resemble familiar shell/file
verbs. Avoid `safe`, `unsafe`, and abstract names such as `mutation`.

Suggested argument shape:

```json
{
  "tool": "file_write",
  "operation": "write",
  "path": "Notes/Foo.md",
  "content": "# Foo\n"
}
```

```json
{
  "tool": "file_write",
  "operation": "replace_text",
  "path": "Notes/Foo.md",
  "old_text": "before",
  "new_text": "after",
  "count": 1
}
```

```json
{
  "tool": "file_write",
  "operation": "batch",
  "operations": [
    {
      "operation": "write",
      "path": "A.md",
      "content": "..."
    },
    {
      "operation": "replace_text",
      "path": "B.md",
      "old_text": "...",
      "new_text": "..."
    }
  ]
}
```

`write` writes full-file content. It defaults to create-only behavior:

- `overwrite: false` or omitted: create a new file and fail if the file exists;
- `overwrite: true`: replace the full file content, creating the file if it is
  missing.

If a create-only write fails because the file exists, the tool should return
`status: "already_exists"` so the agent can ask the user or retry with
`overwrite: true` when the user's intent is explicit.

`replace_text` is the exact text replacement operation for editing within an
existing file.

Partial reads belong on `read` via `start_line` and `line_count`; do not keep a
separate `head` operation in the v0.7.0 contract.

Keep `append` as a first-class operation. It represents a real user intent and is
less brittle than modeling append as a synthetic last-line replacement.

`frontmatter` remains a first-class read operation because context assembly and
workflow scripts use it to inspect many markdown files without loading their
full contents.

`edit_line` remains a first-class write operation. It preserves the existing
line-number and expected-content checks, which cannot be represented faithfully
by a first-occurrence `replace_text` call when a file contains duplicate lines.

`move` accepts `overwrite: false` by default and replaces an existing destination
only when `overwrite: true` is explicit. This folds the old `move_overwrite`
operation into the normal move contract.

Do not retain a separate `truncate` operation. Its behavior is represented by
`write(overwrite=true, content="")`; callers that require existing-file-only
semantics should read or list the target first.

## Breaking Changes

Remove these tool names from the active registry:

- `file_ops_safe`
- `file_ops_unsafe`
- `propose_file_edits`
- `review_create_file`

Add:

- `file_read`
- `file_write`

Existing scripts, workflows, context templates, docs, prompts, and validation
fixtures that reference removed tool names must be updated.

Do not keep long-term aliases. A short migration shim or clear structured error
is acceptable during development, but the v0.7.0 contract should be the new tool
name.

## Architecture

### 1. Tool Registry And Settings

Relevant current contracts:

- ADR 0007: tools are exposed through the settings-backed registry.
- ADR 0008: rich tool guidance belongs in docs/virtual docs, not in always-on
  descriptions.
- `docs/architecture/settings-secrets.md`: built-in tool changes must update the
  settings template.
- `docs/architecture/llm-tools.md`: chat, delegate child agents, and authored
  direct-tool calls resolve tools through shared binding.

Implementation targets:

- Add `enabled_tools` to `settings`.
- Remove `default_chat_tools` from the active contract.
- Update metadata API settings payload to expose `enabled_tools`.
- Update settings reconciliation so removed built-in tools are pruned according
  to the v0.7.0 contract.
- Ensure `enabled_tools` filters the tool registry consistently before tool
  binding.

Affected files likely include:

- `core/settings/settings.template.yaml`
- `system/settings.yaml` for local development only
- `core/settings/store.py`
- `core/settings/__init__.py`
- `api/services.py`
- `api/models.py`
- `static/app.js`
- `static/index.html`

### 2. Tool Binding

Today `resolve_tool_binding(...)` accepts a requested tool value and resolves
configured tools. v0.7.0 should make global enablement a first-class filter.

Required behavior:

- Binding `all` resolves all configured and enabled tools.
- Binding a disabled tool by name fails clearly or omits it with a warning,
  depending on the surface.
- Chat no longer sends a per-chat tool list from the UI. Backend chat start
  resolves enabled chat-visible tools automatically.
- Monty direct tool registration exposes only enabled tools.
- Delegate tool selection honors enabled tools.

Affected files likely include:

- `core/authoring/shared/tool_binding.py`
- `core/authoring/runtime/monty_runner.py`
- `core/chat/executor.py`
- `core/tools/delegate.py`
- `core/llm/capabilities/assistant_tools.py`

### 3. Split File Tool Service Layer

The model-facing file tools must stay thin. Each operation should delegate to
shared core helpers so behavior does not drift.

Target structure:

- one read tool class in `core/tools/file_read.py`;
- one write tool class in `core/tools/file_write.py`;
- shared operation preparation/execution helpers in
  `core/vault_state/file_operations.py` and
  `core/vault_state/file_mutations.py`;
- strict validation per operation;
- structured `ToolReturn.metadata` with stable fields:
  - `tool_name`
  - `operation`
  - `status`
  - `path`
  - `destination` when relevant
  - `error_type` when relevant
  - mutation audit identifiers when a write occurs

Read-only operations execute directly in all modes:

- `read`
- `list`
- `search`
- `frontmatter`

Mutating operations are policy-checked:

- `write`
- `append`
- `edit_line`
- `replace_text`
- `move`
- `delete`
- `mkdir`
- `batch`

### 4. Batch Operation

`file_write(operation="batch", operations=[...])` is the replacement for the
multi-row UX that `propose_file_edits` provided.

Batch rules:

- Batch contains mutating operations only, including `edit_line`.
- `read`, `list`, `search`, and nested `batch` rows are rejected before any row
  executes.
- Operations run in order after approval.
- The backend validates every operation before rendering a review card.
- The review card renders one row per operation.
- User edits become `ToolApproved(override_args={ "operations": [...] })`.
- Denied rows are removed from the approved operation list or represented as a
  no-op decision in a way that gives the resumed model clear feedback.
- If every row is denied, prefer `ToolDenied(message=...)` unless testing shows
  a no-op approved batch gives cleaner model continuation.

The first implementation may execute approved batch operations sequentially and
stop on first failure, returning structured partial-result metadata. Later work
can add transaction-like preflight semantics if needed.

### 5. Collaborative Review Policy

Policy inputs:

- chat mode: `normal` or `collaborative`;
- execution surface: interactive chat, delegate, automation/script;
- operation category: read-only or mutating;
- batch membership.

Initial policy:

- normal interactive chat: allow direct execution;
- collaborative interactive chat: defer `file_write` calls;
- automation/context/workflow scripts: never wait for user review;
- delegate: treat as normal/direct unless a later design explicitly supports
  nested collaborative review.

The policy should be implemented close to tool binding or tool execution, not as
frontend prompt logic.

### 6. Deferred Review Cards

The existing deferred-review spike should be generalized from
`review_create_file` to `file_write`.

Review card row mapping:

- `WRITE @path`
- `APPEND @path`
- `REPLACE @path`
- `MOVE @path -> @destination`
- `DELETE @path`
- `MKDIR @path`

Card behavior:

- pending rows default to no decision;
- approve all and deny all remain available;
- row approvals can include user-edited content, destination paths, or
  replacement text;
- denial reason remains optional;
- submit requires every row to be approved or denied;
- submitted cards lock and collapse;
- follow-up response streams through the existing chat task event path.

Reload support is required before removing the old proposal artifact path:

- pending deferred review cards must render after session reload;
- submitted cards must render as locked historical cards;
- summarization and future agents must see canonical tool review outcome through
  persisted Pydantic message history.

### 7. UI Changes

Remove the chat tool selector from the primary UI.

Chat UI should include:

- model selector;
- thinking selector if still desired;
- context template/workspace controls;
- chat mode toggle: `Normal` / `Collaborative`.

Tool availability remains configurable in System settings through
`enabled_tools`, but it is no longer a normal per-chat choice.

Metadata changes:

- stop sending or using `default_chat_tools`;
- send `enabled_tools` if the frontend needs to display app-wide configuration;
- chat task start requests no longer need `tools` from the composer.

### 8. Documentation Updates

Update current-contract docs only. Do not document this as a long migration
inside product docs unless release notes specifically need migration guidance.

Required docs:

- `docs/architecture/llm-tools.md`
- `docs/architecture/multimodal.md`
- `docs/architecture/vault-state.md`
- `docs/architecture/settings-secrets.md`
- `docs/tools/file_read.md`
- `docs/tools/file_write.md`
- remove or rewrite docs for removed tools
- `RELEASE_NOTES.md`

Because this supersedes prior architecture decisions around tool names, consider
adding an ADR for v0.7.0 tool consolidation after implementation details settle.

## Validation Plan

Scenario targets:

- `integration/core/file_ops_unified_tool`
  - read/list/search smoke paths;
  - write/create/replace/append/move/delete/mkdir paths;
  - structured errors for missing files, conflicts, and invalid args.
- `integration/core/file_ops_batch`
  - batch validates ordered operations;
  - approved batch mutates expected files through vault mutation audit;
  - partial failure behavior is deterministic.
- `integration/core/collaborative_file_ops_review`
  - collaborative chat defers `file_write` while leaving `file_read` immediate;
  - review submission with edited args resumes the same agent turn;
  - chained review requests continue after approval.
- `integration/core/enabled_tools_registry`
  - disabled tools are absent from chat binding and Monty direct tool namespace;
  - missing secret behavior still reports availability correctly.
- Update existing scenarios that reference removed tools.

Manual/browser checks:

- tool selector is gone;
- chat mode toggle is visible and understandable;
- normal mode can write directly through `file_write`;
- collaborative mode renders one review card for one mutating operation;
- collaborative batch renders one multi-row review card;
- pending review survives reload;
- submitted review is locked/collapsed after reload;
- mobile layout remains usable for batch cards.

Fast local checks during implementation:

- `python -m py_compile` for touched Python modules;
- `node --check` for touched frontend modules;
- `python validation/run_validation.py run <targeted scenario>` for narrow
  contracts;
- `git diff --check`.

Maintainers own full validation.

## Implementation Phases

### Phase 1: Contract And Settings

- Add `enabled_tools` setting.
- Remove UI dependence on `default_chat_tools`.
- Remove tool selector from chat UI.
- Make chat task start resolve enabled tools server-side.
- Filter Monty direct tools by enabled registry.
- Add validation for disabled tool behavior.

Phase 1 initial slice:

- Added `enabled_tools` as the app-wide tool availability list in the settings
  template and local development settings.
- Added settings helpers for enabled tool names and enabled tool configs, with a
  temporary fallback to `default_chat_tools` for older runtime settings files.
- Chat task starts now ignore frontend-selected tools and resolve enabled
  chat-visible tools server-side.
- Metadata now exposes `settings.enabled_tools` and no longer exposes
  `settings.default_chat_tools`.
- The chat UI tool selector was removed; the context template selector now
  occupies the remaining settings row.
- Shared tool binding now filters by enabled tools. Explicitly requesting a
  disabled or unavailable tool fails with a clear error.
- Monty direct tool registration now exposes only enabled tools.
- Added `validation/scenarios/integration/core/enabled_tools_registry.py`.

### Phase 2: Split File Tools

- Add `core/tools/file_read.py` for read-only vault operations.
- Add `core/tools/file_write.py` for mutating vault operations.
- Move stable operation implementations into `core.vault_state` helpers so
  tools are thin adapters over shared vault services.
- Keep `file_read` operations limited to `read`, `list`, `search`, and
  `frontmatter`.
- Keep `file_write` operations limited to `write`, `append`, `edit_line`,
  `replace_text`, `move`, `delete`, `mkdir`, and `batch`.
- Add `docs/tools/file_read.md` and `docs/tools/file_write.md`.
- Update default enabled tools to include `file_read` and `file_write`.

Phase 2 initial slice:

- Added `core/tools/file_read.py` and `core/tools/file_write.py`.
- Added service-level operation helpers in `core/vault_state/file_operations.py`
  for the v0.7.0 read/write contract.
- `write` is create-only by default. Existing files return
  `status: "already_exists"` unless the call explicitly passes
  `overwrite=True`.
- `write(overwrite=True)` performs full-file create-or-overwrite behavior for
  clear replacement intent.
- `file_read(operation="read")` supports `start_line` and `line_count`; there
  is no separate `head` operation.
- Added `docs/tools/file_read.md`, `docs/tools/file_write.md`, and
  `validation/scenarios/integration/core/file_ops_unified_tool.py`.
- Added `file_read` and `file_write` to the tool registry and enabled tool list
  while keeping the old file operation tools registered until the later removal
  phase.

### Phase 3: Batch

- Add `operation="batch"` schema and validation.
- Add sequential execution path for normal mode.
- Add structured result metadata for every row.
- Add targeted batch validation scenario.

Phase 3 initial slice:

- Batch is exposed through `file_write`.
- Batch accepts an `operations` list, where each item uses the same operation
  fields as a direct `file_write` call.
- Batch rejects `read`, `list`, `search`, and nested `batch` rows before
  executing anything.
- Batch execution is sequential and non-transactional. A failed row does not
  roll back earlier successful rows.
- Batch metadata includes `total`, `completed`, `failed`, and `results`, with
  each row carrying its own operation metadata and return value.
- Nested batch calls are rejected.
- Extended `validation/scenarios/integration/core/file_ops_unified_tool.py` to
  cover successful batch outcomes and preflight rejection for read rows.

### Phase 4: Collaborative Mode Policy

- Add chat mode state to frontend, API request, and session/resume config.
- Route collaborative `file_write` calls through Pydantic deferred review.
- Generalize deferred-review card rendering for all `file_write` operations.
- Support batch review rows.
- Add reload rendering for pending/submitted deferred reviews.

Phase 4 initial slice:

- Added `chat_mode` to chat task requests. Supported values are `normal` and
  `collaborative`; normal remains the default.
- Added a compact chat settings selector for Normal vs Collaborative edit mode.
- Collaborative mode binds `file_write` with Pydantic deferred approval through
  a chat-only approval override. `file_read` stays immediate so inspection does
  not pause.
- Persisted `chat_mode` in deferred review resume config and retry metadata so
  review continuation and failed-turn retry keep the same mode.
- Extended deferred-review card rendering for `file_write` operations:
  `write`, `append`, `replace_text`, `move`, `delete`, `mkdir`, and `batch`.
- Added `validation/scenarios/integration/core/file_ops_collaborative_policy.py`.
- Updated the deferred-review task skeleton to assert chat mode survives the
  pause/resume cycle.

### Phase 5: Removal And Cleanup

- Complete a parity audit before removing either legacy file tool.
- Move multimodal direct-image and markdown-with-images reads into the shared
  `file_read` service path, preserving policy gates and structured metadata.
- Preserve large vault-read cache behavior for `file_read`.
- Add `frontmatter` to `file_read` and `edit_line` plus move overwrite support to
  `file_write`.
- Update `pending_files` to consume structured `file_read` list/search results.
- Migrate seeded context scripts, workflows, skills, runtime prompts, and direct
  tool examples to the split tools.
- Remove `file_ops_safe`.
- Remove `file_ops_unsafe`.
- Remove `propose_file_edits`.
- Remove `review_create_file`.
- Remove old edit proposal API/UI/storage paths if no longer referenced.
- Update docs, prompts, settings template, validation fixtures, and release
  notes.

Phase 5 file-tool parity slice completed:

- Moved direct-image and markdown-with-images handling into the shared
  `file_read` service path, preserving image policy gates and metadata.
- Added `frontmatter` to `file_read`, `edit_line` to `file_write`, and explicit
  overwrite support to `move`.
- Preserved extensionless markdown resolution, ranged reads, directory-read
  listing, glob-scoped search, virtual mounts, empty-directory cleanup, mutation
  recording, and large-read cache behavior.
- Migrated runtime prompts, packaged context/workflow/skill templates, current
  docs, direct-tool helpers, and maintained validation scenarios.
- Removed the registered and executable `file_ops`, `file_ops_safe`, and
  `file_ops_unsafe` modules. Historical message adapters still recognize old
  tool-event names so prior sessions remain readable.
- Added ADR 0023 and the v0.7.0 release note.

Phase 5 tool cleanup completed:

- Removed `propose_file_edits` and `review_create_file` from the registry,
  settings defaults, Monty exposure rules, virtual docs, and validation targets.
- Older persisted settings explicitly filter both retired names.
- Retained the legacy edit-proposal API/storage renderer only as compatibility
  for cards already stored in existing chat sessions; it is no longer reachable
  through a model-callable creation tool.

## Open Decisions

- Whether batch should stop on first failure or preflight all operations and fail
  before any mutation when one row is invalid.
- Whether submitted deferred review cards need their own persisted lightweight UI
  artifact, or whether canonical tool history plus `chat_deferred_reviews` is
  enough.
